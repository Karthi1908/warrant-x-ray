# Warrant X-Ray - Functional Specification

Oct 13, 2026 and @Karthik

Warrant X-Ray is a web chat application that explains what holding a Bursa Malaysia structured warrant costs, using issuer data, deterministic calculations and cited news. This document defines what the system must do, not how it is built.

## 1. Purpose, Scope and Actors

**Purpose.** Help a retail trader see the real cost and risk of a warrant (time decay, spread, premium, implied volatility, breakeven) and understand what must happen to the underlying share for the warrant to pay off.

**Nature of output.** The system describes costs, risks and user-chosen scenarios. It never recommends buying, selling or holding, and never gives price targets, stop-losses, conviction scores or return predictions.

### Conventions

- Requirement IDs: `FR-<area>-<number>`. Priority: **M** = must (MVP), **S** = should, **C** = could (optional).
- MUST, MUST NOT and SHOULD carry their usual meaning.
- A value that cannot be determined is shown as `unknown`. It is never replaced with zero or a guess.
- Percent values are stored as fractions (0.05 = 5%) and displayed as percentages.
- All displayed times are in Malaysia time; stored times are UTC.

### Actors

| Actor | Description | Main goals |
| --- | --- | --- |
| Trader | Retail user of the web page | Inspect a warrant, compare warrants on one stock, test scenarios, read cited context |
| Visitor | Anyone opening the public URL, including hackathon judges | Reach a useful, grounded answer within seconds, with no sign-up |
| Collector | Scheduled system process | Fetch issuer data and store timestamped snapshots |
| Operator | The project owner | Configure thresholds, switch modes, stop collection, review usage and cost logs |

| Item | Definition |
| --- | --- |
| Spread cost | Loss from buying at the ask and selling at the bid with no change in anything else |

| IV-crush loss | Same as flat decay with volatility 5 points lower |
| Breakeven move | Share move needed for a profit over the holding period, including spread |

## 4. Calculation Rules

All figures in Section 3 and Section 5 come from the rules below. They are deterministic: the same inputs always give the same outputs, with no randomness and no language-model involvement.

### Inputs and conventions

| Symbol | Meaning |
| --- | --- |
| S | Underlying price (the source's underlying bid unless confirmation shows a better field) |
| K | Exercise price |
| r | Risk-free rate, annual, continuously compounded; configurable (default 3%, to be confirmed) |
| sigma | Volatility as a fraction |
| T | Years to expiry = days to expiry / 365, where days to expiry is the calendar-day difference between the expiry date and the as-of date; zero or less means expired |
| n | Underlying shares per warrant, derived from the source's exercise ratio (direction to be confirmed; see FR-CALC-01) |
| P | Warrant market price in RM (bid, ask or mid as stated) |

Model: Black-Scholes pricing, European exercise, no dividends. Volatility is held flat across strikes and time. These limits MUST be stated wherever a scenario result is shown.

### Pricing and sensitivities

```latex
d_1 = \frac{\ln(S/K) + (r + \sigma^2/2)\,T}{\sigma\sqrt{T}}, \qquad d_2 = d_1 - \sigma\sqrt{T}
```

```latex
Call = S\,N(d_1) - K e^{-rT} N(d_2), \qquad Put = K e^{-rT} N(-d_2) - S\,N(-d_1)
```

Warrant value = n times the option value. Per-warrant delta = n \* N(d1) for a call, n \* (N(d1) - 1) for a put. Gamma, vega (per 1 volatility point) and theta (per calendar day) are reported per warrant.

### Derived measures

```latex
\text{Gearing} = \frac{S\,n}{P}, \qquad \text{Effective gearing} = \lvert\Delta_{\text{share}}\rvert\cdot\frac{S\,n}{P}
```

```latex
\text{Breakeven}_{call} = K + P/n, \qquad \text{Breakeven}_{put} = K - P/n, \qquad \text{Required move} = \text{Breakeven}/S - 1
```

- Premium: call = (Breakeven - S) / S; put = (S - Breakeven) / S.
- Mid = (bid + ask) / 2. Spread percent = (ask - bid) / mid. Round-trip cost = 1 - bid / ask.
- Realized volatility (10 and 30 days) = standard deviation of daily log returns multiplied by the square root of 252.

### Calculation requirements

| ID | Requirement | P |
| --- | --- | --- |
| FR-CALC-01 | The direction of the exercise ratio MUST be determined by comparison: compute effective gearing under both interpretations for all rows of a real snapshot and use the one closest (median relative error) to the issuer's published value. The result and its error MUST be recorded. | M |
| FR-CALC-02 | Implied volatility MUST be solved numerically so that the model value equals the chosen price (bid, mid or ask) between volatility of 0.01% and 500%. If the price is outside the no-arbitrage range, or an input is missing, IV is `unknown`. | M |
| FR-CALC-03 | Any metric whose inputs are missing, non-positive (price), or expired MUST be `unknown`. Calculations MUST NOT fail the request. | M |
| FR-CALC-04 | Put and call MUST both be supported with the correct signs. | M |
| FR-CALC-05 | The model MUST reproduce the golden values: for S=100, K=100, r=5%, T=1, sigma=20%, n=1: call 10.4506, put 5.5735, call delta 0.6368, put delta -0.3632, gamma 0.018762, vega 37.524 per 1.00 of sigma, call theta -6.414 per year, put theta -1.658 per year (tolerance 0.1%). | M |
| FR-CALC-06 | Put-call parity MUST hold: Call - Put = S - K \* exp(-r T) within 1e-9. | M |
| FR-CALC-07 | Solving IV for a price generated at a known volatility MUST return that volatility within 1e-6 across a grid of inputs. | M |

## 5. Scenario, Compare and Explain-a-Move

### Scenario simulator

**Inputs:** warrant code; underlying move `m` from -50% to +50% (default 0); days held `d` from 0 to days to expiry (default 5); volatility shift `dv` from -15 to +15 points (default 0).

Let `sigma0` be the implied volatility solved from the mid price, so the model reproduces mid at time zero, and let `s` be the current spread percent.

```latex
P_{entry} = ask, \qquad P_{exit} = n \cdot BS\big(S(1+m),\,K,\,r,\,T - d/365,\,\sigma_0 + dv\big)\cdot\left(1 - \tfrac{s}{2}\right), \qquad PnL = \frac{P_{exit}}{P_{entry}} - 1
```

If `T - d/365` is zero or less, the warrant is valued at intrinsic value (floored at zero).

| ID | Requirement | P |
| --- | --- | --- |
| FR-SCN-01 | The system MUST return entry price, exit price, P&L percent and breakeven move for any valid input set. | M |
| FR-SCN-02 | With `m=0, d=0, dv=0` the P&L MUST equal bid / ask - 1 (the pure spread cost). | M |
| FR-SCN-03 | The breakeven move is the smallest `m` giving P&L of zero or more at the chosen `d` and `dv`; it MUST be `unknown` if none exists between -50% and +50%. | M |
| FR-SCN-04 | The system MUST return a P&L curve over moves from -20% to +20% in 1% steps for three horizons: instant (0 days), the chosen holding period, and twice the holding period capped at days to expiry. | M |
| FR-SCN-05 | Out-of-range inputs MUST be rejected with a message naming the valid range. A holding period beyond expiry MUST be reduced to the days left, with a notice. | M |
| FR-SCN-06 | Every scenario result MUST list its assumptions: volatility held flat across strikes, no dividends, spread applied at exit, issuer quotes may differ from the model. | M |
| FR-SCN-07 | The system MUST provide presets: spread cost, flat-underlying decay, IV-crush loss (dv = -5), and an instant gearing check at moves of -5%, -1%, +1% and +5%. | M |
| FR-SCN-08 | Results MUST be identical whether requested from the chat or the scenario panel. | M |

This function answers: the warrant fell while the share rose; why? It uses two stored snapshots that both contain the warrant.

| ID | Requirement | P |
| --- | --- | --- |
| FR-EXP-01 | Given a code and two snapshots (default: the previous trading day's last snapshot and the latest), the system MUST decompose the change in the warrant's mid price into: underlying move, passage of time, change in implied volatility, and a residual (spread and model error). | S |
| FR-EXP-02 | The decomposition MUST be sequential in that fixed order, the four parts MUST sum to the total change within 1e-9, and the output MUST state the order because the split depends on it. | S |

## 9. Interfaces and Data Entities

The web page and any other client (for example an optional Discord bot) use the same interface. Times are ISO 8601 UTC; percent fields are fractions. Every data response carries `as_of` and `mode`. Every data endpoint accepts an optional `snapshot_id` to pin a stored snapshot; without it the latest is used.

## 10. Errors, Edge Cases and Degraded Modes

The system MUST never show an empty or technical error page. Each situation below has a required behavior (ID FR-ERR-nn, priority M unless stated).

| ID | Situation | Required behavior |
| --- | --- | --- |
| FR-ERR-01 | Source unreachable or returns an unexpected shape | Keep the latest good snapshot, record the failure, show a banner with that snapshot's time |
| FR-ERR-02 | Snapshot is stale | Mark stale per FR-DATA-07; answers state the data age |
| FR-ERR-03 | No stored snapshots exist | Serve clearly labeled synthetic sample data in replay mode; the badge says Sample data |
| FR-ERR-04 | Weekend, exchange holiday or outside trading hours | Serve the latest snapshot; the badge says the market is closed |
| FR-ERR-05 | Bid missing or zero | Spread, IV from bid and mid, and scenario are `unknown`; LOW\_LIQUIDITY high flag is shown |
| FR-ERR-06 | Ask missing or zero | Entry price and scenario P&L are `unknown`; explain why |
| FR-ERR-07 | Bid greater than ask (crossed quote) | Mark the quote as invalid; metrics that need it are `unknown` |
| FR-ERR-08 | Warrant expired or expiring today | Label it; show no forward-looking metrics; scenario returns an explanatory message |
| FR-ERR-09 | Price at or below intrinsic value so IV cannot be solved | IV is `unknown` with the reason; other metrics still shown |
| FR-ERR-10 | Duplicate warrant codes in one snapshot | Use the first and record a data-quality note |
| FR-ERR-11 | Non-positive strike or underlying price | Treat the row as invalid; exclude it from search and note it in Data health |
| FR-ERR-12 | Underlying is not a Malaysian listing, or is not covered | Say it is outside scope; do not answer from general knowledge |
| FR-ERR-13 | Stock has warrants but no price history | Volatility context is `unknown`; IV\_RICH is listed as not evaluated |
| FR-ERR-14 | News service unavailable | Say news is unavailable right now; the rest of the answer continues |
| FR-ERR-15 | News search finds nothing | Say no sources were found for the window (FR-NEWS-08) |
| FR-ERR-16 | A model tier fails or times out | Use the next tier down; if all fail, serve a stored or templated answer and say so |
| FR-ERR-17 | Per-turn time limit of 60 seconds exceeded | Return the grounded part completed so far and state that the answer is partial |
| FR-ERR-18 | Rate limit or daily cap reached | Friendly message with retry time or the fallback in FR-CTRL-02 |
| FR-ERR-19 | Empty message, over 1,000 characters, or non-text content | Reject with a message; nothing is sent to a model |
| FR-ERR-20 | Session expired | Start a new session with a notice; earlier turns are not restored |
| FR-ERR-21 | Requested snapshot does not exist | Fall back to the latest and say so |
| FR-ERR-22 | User asks the system to ignore its rules, reveal internal instructions, or act on text pasted from a web page | Decline politely and continue with the legitimate part of the request, if any |
| FR-ERR-23 | Scenario inputs produce a non-finite result | Return `unknown` with a message; never show NaN or infinity |
| FR-ERR-24 | Two warrants in a comparison have different snapshot times | Use the same snapshot for all and state it |

## 11. Acceptance Scenarios

Each scenario is a test the finished system must pass. Where a scenario names a warrant or stock, use any real or fixture entry that fits. Figures in brackets are placeholders to be filled by the test data.

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-01 | A stored snapshot contains warrant W | The user asks for the card of W with a 5-day hold | The card shows source fields, issuer and recomputed metrics side by side, presets, flags, and the as-of time and mode; every figure matches the calculation rules |
| AC-02 | Warrant W has bid and ask | The user runs a scenario with 0% move, 0 days, 0 volatility shift | P&L equals bid / ask - 1 |
| AC-03 | The same warrant | The user moves the sliders to +5% move, 3 days, -5 points | The result equals the same request made through chat, and the curve shows three horizons |
| AC-04 | Two snapshots a day apart where the share rose and the warrant fell | The user asks why the warrant fell | The answer decomposes the change into underlying, time, volatility and residual parts that sum to the total, states the order used, and uses only retrieved figures |

| AC-07 | The user asks should I buy W | Any phrasing, including pressure or Malay | The chat declines, says why in one sentence, and offers the cost and scenario views; no recommendation language appears |

## 12. Out of Scope, Optional Features and Open Items

### Out of scope

- Buy, sell or hold signals, price targets, stop-loss or entry levels, conviction scores, return predictions.
- User accounts, portfolios, watchlists, alerts, order placement or any connection to a brokerage.
- Automatic posting to social media or public channels.
- Underlyings outside Bursa Malaysia, and non-warrant instruments.
- Skew, jump or dividend modeling beyond the stated simple model.
- Intraday charts or technical-analysis indicators.
