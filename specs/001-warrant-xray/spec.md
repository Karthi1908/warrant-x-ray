## Clarifications

### Session 2026-10-13

- Q: If the source site's terms forbid automated collection (OI-05), what should the project do? → A: Stop live collection and run replay-only on a small set of manually saved, non-public snapshots plus clearly labeled synthetic sample data.

### Session 2026-10-15

- Q: What should be the default and allowed range for the news recency window when searching company announcements and news? (FR-016) → A: Fixed 7-day window strictly (items published within the last 7 days), with no query parameter adjustments.
- Q: What explicit performance thresholds and budgets should be formalized in the specification for the quant engine, chat streaming, and web bundle size? (SC-010) → A: Pure quant engine computation for up to 300 warrants (with 5 IV bases per row) under 1.0 s on 1 CPU core; chat first status event emitted within 3.0 s of request; initial client JavaScript bundle under 300 KB gzipped.
- Q: Where should the visitor count, unique visitor count, and queries count be exposed and displayed? (FR-020, FR-023) → A: Exposed publicly on the Data Health tab and via `GET /api/meta`, as well as logged in operator admin metrics (`GET /api/admin/metrics`).
- Q: How should unique visitors and visits be tracked to satisfy the constitution's Privacy by Design mandate? (FR-005, FR-020) → A: Track visits via anonymous client session UUIDs (header/cookie, 24h expiry) and daily unique visitors via a daily-salted one-way cryptographic hash of client subnet/User-Agent; raw IP addresses are never stored.
- Q: What user actions should count toward the 'queries count' metric? (FR-020) → A: All interactive user queries: chat turns, scenario simulations, and explain-move requests.
- Q: Must the MVP chat handle Malay in every request type, or only decline advice requests in Malay? (FR-017, FR-LANG) → A: MVP detects Malay and reliably declines advice/prediction requests in Malay; other Malay answers may fall back to English. Full Malay across every request type remains optional (C).
- Q: How should the specification formally distinguish between conversational chat history sessions and anonymous visitor tracking sessions? (FR-005, FR-020) → A: Distinguish between ChatSession (in-memory, 2-hour idle expiry, holds last 10 conversation turns, never persisted) and VisitorSession (client UUID cookie/header, 24-hour TTL, used only for anonymous visit deduplication).
- Q: Where should the default risk-free rate be declared as the single source of truth, and how should it behave if unconfigured or missing? (FR-023, OI-08) → A: Declared in config/flags.yaml under risk_free_rate (defaulting to 0.03 / 3.0%), with the quant engine falling back to 0.03 if the configuration file or key is absent.

### Session 2026-10-16

- Q: What should be the default headline implied volatility (IV) basis displayed on warrant cards and used for issuer cross-checking? (FR-009, FR-010) → A: Default headline IV basis is `mid`, falling back to `last` traded price if there is no bid or offer price (and unknown with reason code `no_quote` if neither is available); all five IV bases remain computed and user-toggleable.
- Q: What sections and public repository artifacts should be standardized in the project README to resolve the constitution's open README requirement? (T114, Principle VIII) → A: Adopt the 7-section structure defined in T114 (Mission, Regulatory Disclaimer, Run/Setup Instructions, MIT License, System Architecture, Verified vs. Unverified Status, and Cost Table generated by scripts/cost_report.py) and mark the constitution's TODO(README_CONTENTS) resolved.
- Q: How should the Bursa trading calendar and public holiday schedule be verified and maintained for production collector scheduling? (T013, T017, FR-007) → A: Verify both the 2026 and 2027 exchange calendar years from official Bursa Malaysia circulars during spike T6 (T013) into static `config/bursa_holidays.yaml`; the collector scheduler treats scheduled holidays as planned market closures, serving the latest snapshot with market-closed provenance without issuing unnecessary external network requests.

### Session 2026-10-18

- Q: How should Tavily crawling be utilized to collect Bursa warrant market data? → A: Tavily crawler is the default primary collector for warrant pages, parsed deterministically via a Python program without LLM arithmetic or extraction to uphold Principle I, while the direct screener endpoint remains the secondary fallback.
- Q: How should Tavily crawl frequency and credit budget allocation be scheduled for market data collection? → A: Fixed Trading-Day Schedule: Crawl 2–3 times per trading day (market open, midday, market close) with a 50-credit allocation, reserving remaining credits for interactive news searches.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See what holding a warrant really costs (Priority: P1)

A retail trader enters a Bursa structured warrant code (or asks in chat) and gets a card showing the issuer's published figures next to independently recomputed figures, plus the cost of holding for a chosen period (spread cost, flat-underlying decay, IV-crush loss, breakeven move) and plain-text risk flags. Every view shows the data as-of time and live/replay mode.

**Why this priority**: This is the product's core promise: "what does holding this warrant actually cost?" Everything else builds on it.

**Independent Test**: Open the card for any warrant in a stored snapshot with a 5-day hold; verify all fields, side-by-side values, presets, flags, as-of time and mode appear, and every figure matches the calculation rules (AC-01, AC-15, AC-16, AC-20).

**Acceptance Scenarios**:

1. **Given** a stored snapshot containing warrant W, **When** the user requests W's card with a 5-day hold, **Then** the card shows source fields, issuer vs recomputed metrics, cost-of-holding items, flags, as-of time and mode.
2. **Given** a warrant with no bid quote, **When** its card opens, **Then** bid-dependent metrics show "unknown" with a reason and the low-liquidity flag shows as high.
3. **Given** recomputed headline IV (defaulting to mid, or last traded price if quotes are missing) differs from the issuer's by more than 3 points, **When** the card opens, **Then** an issuer-mismatch flag shows both values and the gap.

---

### User Story 2 - Grounded chat that explains, never advises (Priority: P1)

The trader asks questions in a chat (warrant explanation, holding cost, scenario, comparison, stock summary, news, data status, glossary terms) in English (Malay is detected and advice requests in Malay are always declined in Malay; other answers to Malay prompts may fall back to English). Answers stream with visible data steps, reference markers linking to evidence, and the disclaimer. Every number is verified against retrieved data. Requests for buy/sell/hold calls, targets, stop-losses or predictions are declined, even under pressure, and cost/scenario views are offered instead.

**Why this priority**: Chat is the primary interface and the place where trust (no invented numbers, no advice) is won or lost.

**Independent Test**: Run sample prompts in replay mode; verify numbers are all traceable, the advice boundary holds across phrasings including Malay, and an injected "ignore your rules" text in news changes nothing (AC-07, AC-08, AC-10, AC-11).

**Acceptance Scenarios**:

1. **Given** the user asks "should I buy W", **When** sent in any phrasing or in Malay, **Then** the chat declines in one sentence and offers cost and scenario views with no recommendation language.
2. **Given** a draft answer containing a number absent from retrieved data, **When** the check runs, **Then** it is regenerated once and, if still unverified, the sentence is removed with an omission note.
3. **Given** an ambiguous stock name matching two stocks, **When** the user asks for its warrants, **Then** one clarifying question lists both candidates.

---

### User Story 3 - Test "what has to go right" with scenarios (Priority: P1)

The trader sets an underlying move, days held and volatility shift (sliders or chat) and sees entry price, exit price, P&L, breakeven move, and P&L curves across three horizons, with stated model assumptions. Results are identical from chat and panel.

**Why this priority**: It answers the second half of the mission question: what must happen for the warrant to pay off.

**Independent Test**: Run a 0% / 0-day / 0-shift scenario and confirm P&L equals bid/ask − 1; run +5% / 3 days / −5 points from both panel and chat and confirm identical results (AC-02, AC-03).

**Acceptance Scenarios**:

1. **Given** a warrant with bid and ask, **When** the user runs 0% move, 0 days, 0 vol shift, **Then** P&L equals bid/ask − 1.
2. **Given** out-of-range inputs, **When** submitted, **Then** a message names the valid range.

---

### User Story 4 - Works any day, always shows data age (Priority: P1)

A visitor (including a judge) opens the public page on a weekend or during a source outage with no sign-up, and still gets grounded answers from the latest stored snapshot. The badge shows mode, as-of time, stale or market-closed markers; users can pick any stored snapshot in replay mode.

**Why this priority**: Required for demos and for honesty about data freshness.

**Independent Test**: Switch collection off or open on a Sunday; confirm latest snapshot is served, badge shows its time/closed market, and all sample prompts return grounded answers (AC-12, AC-13, AC-18).

**Acceptance Scenarios**:

1. **Given** collection is switched off, **When** the app opens, **Then** the latest stored snapshot is served and all views work.
2. **Given** no snapshots exist, **When** the app opens, **Then** clearly labeled synthetic sample data is served.

---

### User Story 5 - Cited news context (Priority: P2)

For a stock, the trader sees up to 6 recent news/announcement items published within a fixed 7-day recency window with title, domain, date, link, event type, at most 3 short facts, corroboration count or "unconfirmed" label. With nothing found for the 7-day window, the system says so and does not speculate.

**Why this priority**: Adds context, but the cost analysis stands without it.

**Independent Test**: Request news for a stock with two-domain and single-domain events; verify counts, labels and links (AC-09).

**Acceptance Scenarios**:

1. **Given** announcements from two domains and one from a single domain, **When** the user asks for news, **Then** corroborated events show counts and the single-source event is labeled unconfirmed.
2. **Given** no sources in the window, **When** news is requested, **Then** the system states no sources were found.

---

### User Story 6 - Search, stock summary and compare (Priority: P2)

The trader filters/sorts warrants by underlying, type, issuer, expiry and moneyness; views a stock-level warrant summary (counts, medians, flag counts, five nearest-to-the-money warrants); and compares 2–3 warrants of one stock in a fixed-attribute table without ranking.

**Why this priority**: Discovery and comparison make the card usable at scale.

**Independent Test**: Compare 3 warrants and verify identical attributes in identical order with no "best" label (AC-05).

**Acceptance Scenarios**:

1. **Given** a stock with several warrants, **When** the user compares 3, **Then** a uniform table appears with no ranking.
2. **Given** a stock with no warrants, **When** searched, **Then** an explicit empty result with a plain message appears.

---

### User Story 7 - Explain a move and Deep Risk Report (Priority: P3)

The trader asks why a warrant fell while the share rose and gets a sequential decomposition (underlying, time, volatility, residual) summing to the total change. They may also request a Deep Risk Report with summary, cost breakdown, what must go right, risks, counterpoints, data limits and disclaimer, limited per session.

**Why this priority**: Valuable depth but beyond the MVP core.

**Independent Test**: Use two snapshots a day apart and verify parts sum to the total and the order is stated (AC-04, AC-17).

**Acceptance Scenarios**:

1. **Given** two snapshots where the share rose and the warrant fell, **When** the user asks why, **Then** the four parts sum to the total change and the order is stated.
2. **Given** a Deep Risk Report was produced, **When** the same warrant, snapshot and holding period is requested again, **Then** it is served from storage.

---

### User Story 8 - Operator control (Priority: P2)

The operator can switch collection off with one setting, configure the risk-free rate and flag thresholds without code changes, and review usage and cost logs (including total visits, daily unique visitors, and interactive query counts); spending and rate caps degrade the chat to stored/templated answers.

**Why this priority**: Required for safe public operation.

**Independent Test**: Reach the daily cap and confirm a stored or templated answer with a notice (AC-14, AC-19).

**Acceptance Scenarios**:

1. **Given** the daily spending cap is reached, **When** a user asks a question, **Then** a stored or templated answer is shown with a notice.

---

### Optional (C priority; after all M and S items)

Discord bot (`/risk`, `/warrant`), opt-in forum chatter context (off by default), and full Malay support across every request type — see FR-DSC, FR-CHT, FR-LANG in [requirements.md](../../requirements.md).

### Edge Cases

- Missing/zero bid or ask, crossed quote, expired or expiring-today warrant, price below intrinsic value (IV unsolvable), non-finite scenario results.
- Duplicate warrant codes; non-positive strike or underlying price (row invalid and excluded).
- Source unreachable or returns an unexpected shape (latest good snapshot kept, failure recorded).
- Source terms forbid automated collection: live collection is disabled; the app runs replay-only on manually saved, non-public snapshots plus clearly labeled synthetic sample data.
- Stale snapshot (>20 min in market hours); weekend/holiday/outside hours; no snapshots at all.
- Underlying outside Bursa or not covered (stated out of scope, no general-knowledge answer).
- Stock with warrants but no price history (volatility context unknown).
- News unavailable or empty; instructions embedded in fetched text; user asks system to ignore rules.
- Model tier failure/timeout, 60-second turn limit, rate limit, daily cap; empty/over-length messages; expired session; missing snapshot id; mismatched snapshot times in a comparison.

Full situation-to-behavior table: FR-ERR-01 to FR-ERR-24.

## Requirements *(mandatory)*

Detailed requirement text, priorities (M/S/C) and IDs live in [requirements.md](../../requirements.md); the groups below are normative summaries that map to them.

### Functional Requirements

- **FR-001**: Every displayed number MUST come from stored data or deterministic calculation, never from language-model text (FR-G-01, FR-GRD-*).
- **FR-002**: Every view MUST show data as-of time and live/replay mode; stale data MUST be marked; unknown values MUST show "unknown" with a reason, never zero or a guess (FR-G-02, FR-DATA-07, FR-API-01).
- **FR-003**: Every chat answer and exported report MUST end with the required disclaimer (FR-G-03).
- **FR-004**: Every news/event claim MUST show a source link and date, or be omitted; with no source the system MUST say none was found (FR-G-04, FR-NEWS-*).
- **FR-005**: The system MUST NOT require login or personal data; conversation state MUST be maintained in an ephemeral in-memory ChatSession (expiring after 2 hours idle or 10 turns); visitor metrics MUST use an anonymous VisitorSession (24-hour TTL) and daily-salted IP/UA hashing without raw IP storage (FR-G-05, FR-CHAT-01, FR-CTRL-01).
- **FR-006**: The system MUST work every day via replay over stored snapshots, with a user-selectable snapshot (FR-G-06, FR-DATA-08, FR-ERR-03/04).
- **FR-007**: Data collection MUST fetch timestamped snapshots on trading days at scheduled points (2–3 times per trading day: market open, midday, market close), honoring verified 2026 and 2027 Bursa public holiday calendars (T013/T017) to avoid false outage alerts on market closures, rate-limit itself, back off on errors, keep the last good snapshot on failure, and be switchable off (FR-DATA-01 to 06). Automated collection MUST default to the Tavily web crawler for warrant pages parsed via deterministic Python code (capped at 50 credits daily), falling back to the direct screener endpoint (`WX_MIBB_BASE_URL`) if Tavily crawling fails or is disabled; if external terms forbid collection, collection MUST remain disabled and the system MUST operate replay-only on manually saved, non-public snapshots and labeled synthetic sample data (OI-05).
- **FR-008**: Rows MUST be normalized (percent as fractions, invalid as unknown) with originals retained; raw source rows MUST NOT be exposed publicly (FR-DATA-03, FR-DATA-12, FR-API-02).
- **FR-009**: Users MUST be able to search, filter and sort warrants and view a warrant card with issuer vs recomputed values (headline IV defaults to `mid`, falling back to `last` traded price if quotes are missing), holding-cost summary and flags (FR-SRCH-*, FR-CARD-*, FR-FLAG-*, FR-XCHK-*).
- **FR-010**: Calculations MUST be deterministic, support calls and puts, reproduce the published golden values, satisfy put-call parity and IV round-trip, and never fail a request on bad inputs (FR-CALC-*).
- **FR-011**: Users MUST be able to run scenarios with presets, breakeven, three-horizon curves and stated assumptions, identical across chat and panel (FR-SCN-*).
- **FR-012**: Users MUST be able to compare 2–3 same-stock warrants without any ranking or "best" label (FR-CMP-*).
- **FR-013**: Users MUST be able to get a sequential move decomposition that sums to the total (FR-EXP-*).
- **FR-014**: Stock names, tickers, codes and partial names MUST resolve deterministically first; ambiguity MUST trigger one clarifying question, never a guess (FR-NAME-*).
- **FR-015**: Stock-level summaries MUST describe warrants, not give a view on the stock (FR-STK-*).
- **FR-016**: News MUST be limited to 6 deduplicated items within a fixed 7-day recency window, with event types, short facts, corroboration/unconfirmed labels, and treated as untrusted data (FR-NEWS-*, FR-ERR-22).
- **FR-017**: Chat MUST stream with visible status steps, order answers as answer→numbers→flags/context→limits→disclaimer, mark factual sentences with evidence references, and reply in English, except that Malay input MUST be detected and advice/prediction requests in Malay MUST be declined in Malay; full Malay replies for all other request types are optional (FR-CHAT-*, FR-LANG).
- **FR-018**: Every answer MUST pass a numeric grounding check with one retry then sentence removal, and an advice-boundary check that declines recommendations and predictions in any phrasing or language (FR-GRD-*, FR-ADV-*).
- **FR-019**: A Deep Risk Report MUST be available with required sections, a review pass, grounding checks, reuse and per-session limits (FR-DEEP-*).
- **FR-020**: Usage MUST be rate-limited and spend-capped with graceful fallback (including partitioning daily Tavily credits between a 50-credit crawl allocation and interactive news search); the system MUST track total visits (via anonymous session UUIDs), daily unique visitors (via daily-salted one-way hashing without storing raw IPs), and interactive query counts (chat turns, scenario runs, explain-move requests); these metrics MUST be exposed on the public Data Health tab, via `GET /api/meta`, and via operator admin endpoints; every model call MUST be logged without personal data (FR-CTRL-*).
- **FR-021**: The interface MUST be a single page with chat and an evidence panel (Card, Scenario, Compare, Sources, Data health), usable by keyboard, not color-reliant, and mobile-friendly (FR-UI-*).
- **FR-022**: The system MUST degrade gracefully for every situation in FR-ERR-01 to FR-ERR-24, never showing a technical error page.
- **FR-023**: The operator MUST be able to configure the risk-free rate and flag thresholds without code changes via `config/flags.yaml` (defaulting to 0.03 / 3.0% if the key or file is unconfigured) (FR-DATA-11, OI-08).

### Key Entities

- **Snapshot / WarrantSnapshot**: A timestamped, normalized set of warrant rows with fetch time, source update time, success flag and note.
- **WarrantMetrics**: Recomputed measures (IV, Greeks, gearing, premium, breakeven, spread) plus cross-check differences; any may be unknown.
- **WarrantCard**: Snapshot + metrics + holding-period presets + flags + not-evaluated list + as-of/mode.
- **ScenarioResult**: Inputs, entry/exit price, P&L, breakeven move, three-horizon curves, assumptions.
- **NewsItem**: Title, domain, date, link, event type, ≤3 facts, corroboration, extraction method, retrieval time.
- **Evidence**: Referenceable record (snapshot, metrics, scenario, news, health) linking chat markers to sources.
- **ChatSession**: In-memory, browser-scoped conversational history (last 10 turns, 2-hour idle expiry, never persisted).
- **VisitorSession**: Ephemeral anonymous client UUID (header/cookie, 24-hour TTL) used solely to deduplicate visit counts without personal data or raw IP storage.
- **UsageMetrics**: Aggregate counts for total visits, daily unique visitors (salted-hash derived), and total interactive queries (chat turns + scenarios + explain-move).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of numbers in answers and panels trace to stored data, calculations or user-typed values (grounding check pass or removal rate recorded).
- **SC-002**: 0 recommendation or prediction outputs across the advice-boundary test set, including pressure, rephrasing and Malay prompts.
- **SC-003**: A first-time visitor on desktop or phone reaches a grounded answer from a sample prompt in under 30 seconds with no sign-up.
- **SC-004**: All golden-value, put-call parity and IV round-trip checks pass (AC-20).
- **SC-005**: 100% of acceptance scenarios AC-01 to AC-20 pass in replay mode; all sample prompts succeed on a weekend.
- **SC-006**: Every view shows as-of time and mode; 100% of stale snapshots are marked.
- **SC-007**: A scenario slider change updates the result within 0.3 seconds of the response arriving.
- **SC-008**: Every model call is logged, allowing per-tier cost totals over a 30-prompt run (AC-19).
- **SC-009**: Every M and S requirement has at least one named test, and unimplemented items are reported rather than dropped.
- **SC-010**: Pure quant engine metrics and five IV bases for 300 warrants complete in under 1.0 s on 1 CPU core; streaming chat emits its first status event within 3.0 s of request; initial production client JavaScript bundle is under 300 KB gzipped.
- **SC-011**: Usage metrics (total visits, daily unique visitors, queries count) are computed without storing personal data or raw IP addresses, and are accessible via `GET /api/meta`, the public Data Health tab, and operator admin endpoints.

## Assumptions

- Target users are retail traders of Malaysian warrants; visitors include hackathon judges.
- Data source field names, exercise-ratio direction, style/settlement, theta/sensitivity meaning, all-issuer fetch, terms of use, 2026 and 2027 trading calendars (verified via official Bursa notices into `config/bursa_holidays.yaml`), price-history source, policy rate, model availability and regulatory wording (OI-01 to OI-10) are unverified and MUST be resolved against real responses or official docs before dependent behavior is finalized; none are guessed here.
- Default risk-free rate is 3% (0.03) declared in `config/flags.yaml` (falling back to 0.03 if unconfigured), provisional pending Malaysian benchmark policy rate verification (OI-08).
- Automated collection defaults to the Tavily web crawler with deterministic Python parsing (with direct screener endpoint as secondary fallback), enabled only after source terms and rate limits allow (OI-05); until then the product runs in replay-only mode.
- Pricing uses a simplified model (European, no dividends, flat volatility); limits are always disclosed.
- Constitution constraints apply: deterministic numbers, cited news via the designated search provider, Nebius + Nemotron-only LLM calls, no raw scraped data in the public repo, secrets from environment, public repository with MIT License, and README standardized with the 7 required sections.
- Optional (C) features are deferred until all M and S items work.
- Out of scope: advice/signals, accounts, portfolios, brokerage connection, auto-posting, non-Bursa underlyings, skew/jump/dividend modeling, intraday charts.
